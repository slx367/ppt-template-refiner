# 技术表达

## 用工具解决什么问题

技术页回答：输入什么、如何处理、有什么约束、输出什么、用于什么决策。工具名称放在对应模块旁，避免堆框架图标却不讲工作过程。

候选布局：左侧约 60% 展示集成关系，右侧约 40% 展示三项技术关键，底部一句具体成果。比例只是选项，服从模板和内容。模块可写“模块名 + 承担工作 + 已核实工具”。不为了画闭环编造自动反馈。

- 功能：用户能完成的动作，如查询状态、比较方案。
- 技术难点：跨节点状态一致、保护执行中任务、结果复现等实现约束。
- 创新：相对于明确基线的新方法、机制或适用条件，需要比较证据。证据不足称技术关键或拟研究方向。

项目介绍兼顾系统全貌与核心贡献。突出某模块时增加输入、计算、输出、实例和验证安排，而不是重复模块名称。

## 适配版面的文字

保留用户指定主题词，用具体能力作标题，不机械写“某某优势”。用户只要求去掉“优势”，不能误删“调度”“韧性”等主题词。

示例结构：一行标题 + 两行解释。

**多约束协同调度**
统筹任务、资源与库存限制
保留执行中任务，调整后续作业

**作业链韧性量化评估**
衡量受扰后的服务损失与恢复时间
定位影响作业链恢复的薄弱环节

**调度与韧性协同决策**
将评估结果用于调度方案比较
兼顾运行效率、恢复效果与调整代价

以上是措辞示例，不代表功能已实现，也不要求其他行业使用这些主题。按项目实际状态标注已实现或拟建设。依据截图容量拟稿，不返回放不下的段落。

## 算法和公式

先确定展示模块，公式数量服从可解释性。用户不希望某模块加公式时，用步骤、约束或输入输出表达；禁用某技术时，不换同义词加入。

每个公式交代变量、单位/范围、时间窗口、数据来源和用途。候选算法与已实现算法分开，不能只堆算法名，也不能无证据声称全局最优。

评估模块可按“性能基线—受扰损失—恢复过程—策略比较”组织；先确定业务指标与恢复判据，再选数学表达，保证窗口和归一化口径一致。不要默认所有项目都要韧性评估或仿真。

## 计划具体化

把“完善平台、提升能力”改成“实现对象 + 输入输出 + 验收方式”。例如：“新增指标模块，读取运行日志与任务记录，输出损失和恢复时间，以预设算例核对计算。”仍是计划时明确标为下一步，不改写成已建成成果；不添加虚构时间、合作方或性能数字。
